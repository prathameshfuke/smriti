## 3. Offline-First Data Flow

### 3.1 Write Path (Patient plays game → data stored)
```
Patient taps answer
    → Game component captures event
    → Telemetry logger creates event object:
      {
        id: uuid(),
        patientId, gameType, difficulty, timestamp,
        responseTimeMs, isCorrect, touchCoordinates,
        sessionId, synced: false
      }
    → Dexie.js writes to IndexedDB `telemetry_events` table
    → Scoring engine updates local `daily_summary`:
      { date, gameType, accuracy%, avgReactionMs, sessionCount }
    → Difficulty engine checks if adjustment needed
    → UI updates immediately from local state
```

### 3.2 Sync Path (Device goes online)
```
Service Worker detects connectivity (navigator.onLine + fetch probe)
    → Sync engine reads all records where synced === false
    → Batches into chunks of 50 events
    → POST /api/sync with delta payload:
      {
        patientId,
        events: [...],          // Raw telemetry
        dailySummaries: [...],  // Aggregated scores
        reminderAcks: [...],    // Reminder acknowledgments
        lastSyncTimestamp
      }
    → Server writes to Supabase
    → Server returns:
      {
        serverTimestamp,
        updatedProfiles: [...], // Caregiver may have edited remotely
        updatedReminders: [...] // New/changed reminder schedules
      }
    → Sync engine applies incoming changes (LWW by updatedAt)
    → Marks local events as synced: true
    → Updates sync status indicator
```

### 3.3 Conflict Resolution Strategy
| Data Type | Strategy | Rationale |
|-----------|----------|-----------|
| Telemetry events | Append-only (no conflicts possible) | Events are immutable facts |
| Daily summaries | Server recomputes from events | Single source of truth |
| Patient profiles | LWW by `updatedAt` timestamp | Caregiver edits win |
| Reminder schedules | LWW by `updatedAt` | Caregiver is the authority |
| Game difficulty level | Local device is authoritative | Device has latest performance data |

## 5. Authentication Flow

```
Caregiver opens app for first time
    → Supabase Magic Link (email) or Phone OTP
    → On success: JWT stored in httpOnly cookie
    → Caregiver creates patient profile(s) locally
    → Patient profiles synced to Supabase on connectivity

Patient mode (no auth required):
    → Caregiver taps "Start Session for [Patient Name]"
    → Patient interacts with games — no login needed
    → All data tagged with patientId from caregiver's profile

Caregiver dashboard:
    → Requires active session (JWT)
    → Shows only patients linked to this caregiver's account
    → Supabase RLS enforces: caregiver can only see their own patients
```

## 6. API Endpoints (Next.js API Routes)

### POST /api/sync
- Receives batched telemetry + daily summaries + reminder acks
- Writes to Supabase
- Returns updated profiles/reminders changed since lastSyncTimestamp
- Rate limited: max 1 sync per 30 seconds per device

### POST /api/auth/login
- Initiates Supabase Magic Link or Phone OTP

### GET /api/patients
- Returns caregiver's patient list with latest summary scores
- Supabase RLS filtered

### GET /api/patients/[id]/timeline
- Returns longitudinal score data for dashboard graphs

### POST /api/alerts/check
- Server-side alert evaluation (2SD drop detection)
- Returns alert status per patient
- Called during sync or on dashboard open

## 8. Performance Budget

| Metric | Budget | Strategy |
|--------|--------|----------|
| JS bundle | <150KB gzipped | Code splitting per route; no heavy UI libraries |
| CSS | <30KB | Tailwind with purge; no component library CSS |
| Images (game assets) | <2MB total | WebP format, compressed, lazy-loaded |
| Audio (per language) | <15MB | MP3 64kbps mono; cached on install |
| First load (3G) | <3 seconds | SSR + streaming + prefetch |
| Subsequent loads | <500ms | Service Worker cache-first |
| IndexedDB operations | <10ms | Dexie.js bulk operations; indexed queries |
| Game frame rate | 60fps | No heavy animations; CSS transforms only |

## 9. Security

- All API routes validate Supabase JWT
- Row Level Security on every Supabase table: `auth.uid() = caregiver_id`
- No patient PII in URL parameters or query strings
- Patient names stored encrypted (Supabase Vault or application-level)
- Telemetry contains no PII — only patientId (UUID), scores, timestamps
- HTTPS enforced (Vercel default)
- Content Security Policy headers set
- No third-party analytics SDKs (privacy-first)
